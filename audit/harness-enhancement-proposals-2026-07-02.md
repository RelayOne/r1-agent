# Harness enhancement proposals — design panel (wave 3, 2026-07-02)

Three architect agents (reliability / power / operability lenses) each read the live code and proposed the highest-leverage enhancements NOT already in the audit backlog. Each cites file:line. Ranked within lens by leverage-per-effort. Status: the 11 S/low + M/low proposals below were IMPLEMENTED on this branch (marked ✅ with commit). The 3 remaining (P3 review-dissent-retry, P5 descent A/B, P6 execute-mode specexec, R6 WAL rotation, O2 daemon-cancel, O3 logs-follow, O5 grace-drain) are the medium/high-risk set, left as the next wave.

## Reliability lens (6)

### R1. Fail-closed no-result detection in ClaudeRunner: stop marking dead CLI runs as successful empty tasks  `[S/low-risk]`
> ✅ IMPLEMENTED (commit: 6ae36a29)
**Why:** A claude CLI that exits nonzero or is killed before emitting a 'result' event returns RunResult{IsError:false} with err=nil (internal/engine/claude.go:183-197 sets only ExitCode; stderr discarded at :144). Workflow only checks IsError (workflow.go:685-689), verifies the UNCHANGED worktree against a green baseline, hits ErrNothingToCommit and breaks as success (workflow.go:1171-1177, 1304), and cmd/r1/main.go:552-561 marks the task Success:true / StatusDone. Expired auth, a CLI flag break after upgrade, OOM, or a boulder/Ctrl-C kill silently converts into 'task done, zero changes' — the worst possible failure mode for an agent harness. Codex already does this right (codex.go:155-162 sets IsError=true on nonzero exit), so this is also a parity bug vs CLAUDE.md design decision 27.

**What:** internal/engine/claude.go Run(): track resultSeen in the event loop (:156-177); after cmd.Wait, if !resultSeen or ExitCode!=0, set result.IsError=true with Subtype 'no_result'/'error_during_execution' (or 'cancelled' when ctx.Err()!=nil), and capture bounded stderr instead of discarding it (:144) so the failure reason survives. internal/workflow/workflow.go: after execRunner.Run (:669), check execCtx.Err() and return ctx.Err() instead of misclassifying cancellation as agent failure. Tests: claude_test.go case for exit-1-no-result; workflow mockrunner_test.go case asserting no StatusDone on empty no-result run.

### R2. git merge --abort on all Merge failure/timeout paths so a failed merge can't wedge the main repo  `[S/low-risk]`
> ✅ IMPLEMENTED (commit: ce239239)
**Why:** worktree.Manager.Merge runs merge --abort only when applyConflictResolutions fails (manager.go:302-304). The generic 'git merge' failure path (:307-308) and both timeout paths (:260-262, :294-296 — CommandContext SIGKILLs git mid-merge after 2min) leave MERGE_HEAD + a conflicted index/working tree in the user's RepoRoot. workflow.go:1199-1216 only ResetMainTo when HEAD moved, and a conflicted merge never moves HEAD, so nothing cleans it. Since mergeMu serializes all merges, one wedged merge makes every subsequent task's merge fail ('MERGE_HEAD exists') — repo-wide stall that requires manual git surgery. (Distinct from audit A013, which fixed conflict parsing + test coverage, not abort semantics.)

**What:** internal/worktree/manager.go Merge(): add an abortInProgressMerge(ctx) helper that checks for .git/MERGE_HEAD and runs 'git merge --abort' (fallback 'git reset --merge'); call it (a) on the generic merge-failure return :307-308, (b) on both timeout returns :260-262/:294-296 using a fresh context since mergeCtx is dead, and (c) as a preflight at Merge entry so a stale wedge from a crashed prior run self-heals. Regression test in integration_test.go: force a real-merge failure (dirty main working tree) and assert MERGE_HEAD absent and a follow-up merge succeeds.

### R3. hub.Bus observer drain: stop losing terminal governance/ledger writes to the deferred governor.Close race  `[M/low-risk]`
> ✅ IMPLEMENTED (commit: 5617fe05)
**Why:** hub Observe dispatch and EmitAsync are untracked fire-and-forget goroutines (internal/hub/bus.go:222-231, :248-254; no WaitGroup/Drain/Close exists in the package). The Governor is a wildcard ModeObserve subscriber that writes ledger nodes and v2 bus events for task lifecycle, declarations, cost, and review verdicts (internal/governance/governance.go:135-160), EventTaskCompleted is emitted via emitEventAsync (workflow.go:1233-1242), and app.go:294-295 defers governor.Close() — so on every normal run the final worker.declaration.done / cost / lifecycle writes race a closed bus+ledger and are silently dropped ('bus: closed'). workflow.go:2311-2321 documents this exact hazard and hand-patched only the review event. The V2 audit trail is missing its terminal records nondeterministically.

**What:** internal/hub/bus.go: add a sync.WaitGroup to Bus; wrap the Phase-3 observe goroutines and the EmitAsync goroutine in wg.Add/Done; add Bus.Drain(ctx context.Context) error that waits with timeout. internal/app/app.go: in the Run teardown (before the governor.Close defer at :294 fires — reorder defers or call explicitly), call o.eventBus.Drain(5s). Optionally demote the emitReviewEvent special-case comment (workflow.go:2311) to reference the drain guarantee. Test: hub bus test emitting N events to a slow ModeObserve subscriber, asserting Drain returns only after all handlers ran; governance integration test asserting declaration node exists in ledger after orchestrator.Run returns.

### R4. Ledger index self-heal on open + busy_timeout: prevent permanent node invisibility and Merkle chain forks  `[S/low-risk]`
> ✅ IMPLEMENTED (commit: 975b3d1c)
**Why:** A crash or InsertNode failure between store.WriteNode (ledger.go:292) and index.InsertNode (ledger.go:295) leaves a durably-written node invisible to every query forever: RebuildIndex (ledger.go:644) has zero production callers and ledger.New (ledger.go:139-155) never validates index freshness. The index DSN lacks _busy_timeout (index.go:22, '?_journal_mode=WAL' only — session.db at sqlstore.go:53 got this right), so a second r1/desktop-rpc process touching the same .stoke/ledger gets instant SQLITE_BUSY, triggering exactly this drift. Because AddNode derives ParentHash from latestInMissionUnlocked via the index (ledger.go:264-270, 306-325), a dropped index row silently forks the STOKE-002 Merkle chain — later Verify/migration divergence checks fail with no path back.

**What:** internal/ledger/index.go NewIndex: add _busy_timeout=5000 to the DSN. internal/ledger/ledger.go New(): cheap consistency probe — compare 'SELECT COUNT(*) FROM nodes' against the store's chain-file count (add Store.CountNodes walking the chain tier, or persist a monotonic write counter) and call RebuildIndex() on mismatch, logging the heal. Also make AddNode/AddEdge attempt one immediate InsertNode/InsertEdge retry-or-rebuild before surfacing the error. Tests: ledger_test.go case that deletes .index.db rows post-write and asserts New() heals + ParentHash chain stays linear.

### R5. Scheduler: stop dispatching queued tasks after cancellation and stop recording cancellation as task failure  `[S/low-risk]`
> ✅ IMPLEMENTED (commit: 27bd0ff5)
**Why:** Scheduler.Run's dispatch section (internal/scheduler/scheduler.go:189-222) never checks ctx.Err(); only the blocking select (:267-281) reacts to Done. On Ctrl-C/timeout, every still-queued ready task is dispatched into a dead context, fails with 'context canceled', and cmd/r1/main.go:511-543 writes a failure Attempt record and markTask StatusFailed for work that never ran — corrupting attempt numbering (NextAttemptNumber), failure-fingerprint escalation, and wisdom: workflow.go:1291-1301 records cancellation-induced 'signal: killed' analyses as learned gotchas that later get injected into unrelated retry prompts. Resume then sees phantom failed tasks.

**What:** internal/scheduler/scheduler.go Run(): at loop top, if ctx.Err()!=nil skip the dispatch section and fall through to the in-flight drain (reuse :273-279), returning results for dispatched tasks only. cmd/r1/main.go execFn (both call sites ~:511 and ~:1498): when errors.Is(err, context.Canceled), skip store.SaveAttempt and markTask, leaving the task StatusPending for resume. internal/workflow/workflow.go: skip the Wisdom.Record gotcha (:1291) when execCtx.Err()!=nil. Test: scheduler_test.go case cancelling mid-run with queued tasks, asserting undispatched tasks produce no results and no failed-state entries.

### R6. Bus WAL rotation + fired-delayed compaction: bound the governance bus's disk and memory growth  `[M/medium-risk]`
**Why:** Every governance.New (once per app.Run, internal/app/app.go:272) opens the shared <stateDir>/governance/bus WAL (governance.go:81) and OpenWAL.replayIndex loads EVERY event ever published into an in-memory map (internal/bus/wal.go:66-87), with Append growing it further (:114) — startup cost and RSS grow linearly forever across missions, and the r1 mcp-serve daemon (cmd/r1/mcp_serve_runtime.go:84) holds it all resident. events.log/delayed.log have no rotation or compaction, and fired delayed events never write a consumed record (bus.go:814-824, :882-892), so ReadDelayed (wal.go:208-246) replays them as pending after restart — duplicate delivery the moment any producer adopts PublishDelayed (supervisor timeout rules are the designed consumer). Silent degradation today, refire bug tomorrow.

**What:** internal/bus/bus.go: in both delayed-timer callbacks, append a consumed record via w.AppendDelayedCancel(cancelID) before Publish. internal/bus/wal.go: (1) segment rotation — roll events.log at a size threshold (e.g. 64MB) to events-<n>.log with ReadFrom scanning segments in order; (2) replace the full Event index with an ID->segment/offset map or bounded LRU (FindByID is only used for the causal-ref check at bus.go:417-424, which tolerates miss-as-allow); (3) compact delayed.log on open by rewriting only still-pending entries. Tests: restart test asserting a fired delayed event does not refire; rotation test asserting ReadFrom spans segments.
