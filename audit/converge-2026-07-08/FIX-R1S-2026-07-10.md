## Goal

The r1-demo-admin redirected unauthenticated users to the coord-api SSO start
(`r1-demo-coord-api /v1/auth/sso/start`), which returned
`{"error":"SSO not configured (RELAYONE_SSO_* env unset)","ok":false}` (HTTP 503).
Interactive browser sign-in was not wired — the admin only worked via a
directly-minted operator JWT. Goal: configure `RELAYONE_SSO_*` so a human can
click-sign-in to the r1 admin via the LIVE RelayOne demo OIDC.

## Result — DONE (full round-trip works headlessly)

- `/v1/auth/sso/start` now **302-redirects to the live RelayOne authorize URL**
  (the "not configured" error is gone).
- The full OIDC authorization-code exchange completes end-to-end headlessly:
  login as demo-admin -> authorize -> callback -> a valid r1 JWT is minted.
- That SSO-minted JWT loads the **admin dashboard (HTTP 200)**.

## Contract discovered (source)

The coord-api uses `auth.RelayOneSsoClient`
(`services/r1-coord-api/internal/auth/sso.go`), NOT the `internal/auth.SsoClient`.
Env it reads (`services/r1-coord-api/main.go:322-331`):
`RELAYONE_SSO_BASE`, `RELAYONE_SSO_CLIENT_ID`, `RELAYONE_SSO_CLIENT_SECRET`,
`RELAYONE_SSO_REDIRECT_URI`. It is a **confidential** client
(`client_secret_post`, creds in the token-request body), **no PKCE**.

- Authorize URL = `{BASE}/oauth/authorize?response_type=code&client_id&redirect_uri&scope=openid+email+profile+msp&state`
- Token = POST `{BASE}/oauth/token`; Userinfo = GET `{BASE}/oauth/userinfo`.

Live issuer discovery (`.../.well-known/openid-configuration`) puts endpoints
under `/v1/oauth/*`. The coord-api client hardcodes `/oauth/*`, so BASE is set to
include `/v1`: `BASE + /oauth/authorize` == the real `/v1/oauth/authorize`.
**Zero coord-api path/code change needed for the redirect.**

## What was configured

### 1. OIDC client seeded in the LIVE control-plane DB (demo/synthetic)

`oauth_clients` was empty. The control-plane admin API
(`POST /v1/admin/oauth-clients`) requires a platform-admin session AND restricts
`allowedScopes` to a subset that excludes `msp`/`org` — it would have rejected the
coord-api's hardcoded `msp` scope. So the client was seeded directly into the
`relayone_demo` DB (Cloud SQL `resolute-parity-484218-g1:us-central1:honest-demo-sql`,
secret `honest-demo-relayone-database-url`). `client_secret_hash` = `sha256hex(secret)`
(matches `oidc-provider.service.ts:843` verification).


### 4. Code fix (r1-agent) — token-request anti-CSRF header

The token exchange initially failed at the callback with
`token endpoint 403: csrf_header_missing`. The control-plane's `CsrfGuard`
(`common/auth/csrf.guard.ts`) requires a custom header `X-CSRF-Protection: 1` on
every cookie-less state-changing POST, exempting only requests carrying an
`x-api-key`/`relayone-api-key` header or `Authorization: Bearer`. The coord-api's
token POST authenticates via `client_secret_post` (creds in the body), so it
matched no exemption. Fix (R1 side, within commit boundary — NO control-plane
change): `ExchangeCode` now sends `X-CSRF-Protection: 1`.
Files: `services/r1-coord-api/internal/auth/sso.go` (+ test assertion in
`sso_test.go`). `go build/test/vet` green; image rebuilt + redeployed
(revision `r1-demo-coord-api-00003-hc2`, image digest
`sha256:5ef8de8cfe2693bf2347c22601e7e9e130b3666b1bac525fa97beffa44e06368`).

### 5. Demo-data: operator role for demo-admin

`hasOperatorRole` (r1-admin `main.go:892`) requires the literal role `operator`.
The RelayOne demo user `demo-admin@goodventures.ca` carried only the RelayOne org
role `admin`, so the SSO-minted JWT (`roles:["admin"]`) got 403 at the dashboard.
Granted the demo user an `operator` `role_assignment` in `relayone_demo` (the
claims service maps `role_assignment.role` straight into the `roles` claim —
`oidc-claims.service.ts:146`). The demo admin is meant to operate the demo, so
this is demo data, not a code/product change.

## Honest caveats / known gaps

1. **Claim-name mismatch (`msp`/`org` empty).** The coord-api reads JSON fields
   `msp`/`org`; the control-plane emits `msp_org_id`/`org_id` (+ `roles`). So `msp`
   and `org` come back empty in the r1 JWT. `roles` matches by name and carries
   through. Honest Demo is a single-tenant org anyway (no MSP context). Not a
   blocker for auth; a claim-mapping refinement if MSP/org context is ever needed.
2. **Pre-existing token-paste gap (out of scope).** The coord-api callback returns
   the r1 JWT as JSON; it does not set an admin session cookie and redirect back to
   the admin. So a real browser click-through lands on the callback JSON page with
   the JWT, which the user then supplies to the admin as a bearer token — the
   "token-paste flow" already documented at r1-admin `main.go:744-746`. Wiring the
   callback to install the JWT + redirect to the admin dashboard is an r1-admin/
   coord-api enhancement beyond this SSO-config task.
3. **Operator role is demo data** (see §5) — granting `demo-admin` the r1
   `operator` role in the RelayOne demo DB. The alternative (a RelayOne-role ->
   r1-role mapping in the coord-api `Login`) is a product decision left to the user.
