# Round-2 fix review — confirmed issues (2026-07-06)

Adversarial review of the round-2 fixes. 5 confirmed (incomplete-fixes + 1 regression). Plus 3 pre-existing wall-clock/timing tests flake under the full parallel container suite (migration RoundTrip1000Turns 60s budget, cmd/r1 daemon tick window, walkeeper restart) — my round-2 additions increased load and tipped them; they pass in isolation.

## [HIGH/incomplete-fix] Concern scope filter is inert for dissent/advisory nodes (and the branch_ref dimension is dead) — cross-loop leak persists
`internal/concern/sections/sections.go:59`

filterByScope keys on the node content fields loop_ref / task_dag_scope / branch_ref and keeps any node that lacks the field (treated as mission-global). But the actual node schemas for the sections the fix documents as newly-scoped do NOT carry these fields. The canonical Dissent node (internal/ledger/nodes/agree_dissent.go, NodeType "dissent", which is exactly the type DissentHistory queries) has only draft_ref/dissenting_stance_id/reasoning/requested_change/severity/research_refs — no loop_ref, no task_dag_scope, no branch_ref (it ties to a loop only indirectly through its draft). SDMAdvisory carries branches_involved (an array) but no branch_ref/loop_ref/task_dag_scope. Grepping internal/ledger/nodes shows branch_ref is written by ZERO node types, so scope.BranchID never filters anything for any section. Net: the doc comments on DissentHistory and SDMAdvisories ("Results are scoped to the current loop/task/branch") are false in practice; only decision nodes (which really do carry loop_ref/task_dag_scope) are actually scoped. The new sections_test.go passes only because addNode() hand-injects synthetic loop_ref/branch_ref keys that real Dissent/SDMAdvisory nodes never marshal, so the test does not exercise the real schema.

**Scenario:** Mission m1 runs two consensus loops loop-A and loop-B. Each loop records real Dissent nodes (type "dissent") via the ledger; those nodes carry draft_ref but no loop_ref. When BuildConcernField projects a stance in loop-B (sScope.LoopID="loop-B"), DissentHistory queries all type="dissent" nodes in m1 and calls filterByScope with LoopID="loop-B". Because no dissent node has a loop_ref content field, every node is kept as "global" — loop-A's objections leak verbatim into loop-B's concern projection, the exact cross-scope leak this fix claims to close.

**Fix:** Either populate loop_ref/task_dag_scope/branch_ref on Dissent/SDMAdvisory nodes at write time, or scope these sections through the edge graph (dissent.draft_ref -> draft.loop_ref) instead of a content-field match, and drop/replace the never-populated branch_ref dimension. Change the tests to build nodes via the real node structs so schema drift is caught.

## [MEDIUM/incomplete-fix] NormalizeModel over-broad substring match mis-prices gpt-4o-mini (and o3 variants) and suppresses the unknown-model signal
`internal/costtrack/tracker.go:344`

NormalizeModel resolves tiers with unanchored substring tests. `case strings.Contains(m, "gpt-4o"): return "gpt-4o", true` matches the distinct, much cheaper model gpt-4o-mini, because "gpt-4o-mini" contains "gpt-4o". There is no "gpt-4o-mini" key in ModelPricing, so the exact-match short-circuit at the top does not save it. Result: gpt-4o-mini is priced at gpt-4o rates ($2.5/M in, $10/M out) instead of its real ~$0.15/$0.60 — roughly a 16x over-count. The same over-broad pattern applies to the `strings.Contains(m, "o3")` branch: o3, o3-pro, o3-2025-* all collapse to o3-mini pricing (an under-count for the full o3 tier). Worse than a raw misprice: because NormalizeModel returns matched=true, ComputeCost takes the confident path and does NOT increment unknownModelHits / fire OnUnknownModel — so the very observability signal this fix added to make mispricing visible is silenced for exactly these mis-matched names. Before the fix these unknown names fell to the Sonnet default AND were (by intent of the new signal design) meant to be flagged; now they are silently and confidently mispriced.

**Scenario:** costtrack.ComputeCost("gpt-4o-mini", 1_000_000, 200_000, 0, 0) returns gpt-4o pricing = 2.5 + 2.0 = $4.50 instead of the true gpt-4o-mini cost (~$0.27), a ~16x overcount, and UnknownModelHits() does not increment because NormalizeModel returned matched=true. Symmetrically ComputeCost("o3-pro", ...) is priced as o3-mini (undercount) with no unknown-model signal.

**Fix:** Match tier keywords against word-boundary/prefix-aware tokens rather than raw Contains, or check the more specific names first (e.g. handle "gpt-4o-mini", "o3-mini", "o3-pro" as their own keys/branches before the broad "gpt-4o"/"o3" fallbacks). At minimum add explicit ModelPricing entries + branches for gpt-4o-mini and o3 full so the substring fallbacks cannot capture them, and add a test asserting NormalizeModel("gpt-4o-mini") != "gpt-4o".

## [MEDIUM/regression] patchapply modify path now clobbers symlinked/hardlinked targets (temp+rename replaces the link instead of writing through it)
`internal/patchapply/patch.go:282`

The atomicity fix swapped the modify-path writer from os.WriteFile(fullPath, ...) to atomicWriteFile(fullPath, ...), which stages a temp file in filepath.Dir(fullPath) and does os.Rename(tmp, fullPath). os.WriteFile opens the path with O_TRUNC and FOLLOWS symlinks — it writes THROUGH a symlink into the real target, and for a hardlinked file it truncates+rewrites the same inode, so all link siblings stay in sync. os.Rename REPLACES the path entry: it removes the symlink (or one hardlink) and puts a brand-new regular-file inode there. So when a patched source file is a symlink, applying a modify hunk now destroys the symlink, writes the new content to the link location as a regular file, and leaves the intended target file with its OLD content. Readers via the symlink path see new content; readers via the real target see stale content — a silent divergence. The same rename breaks hardlink groups (new inode, siblings unchanged). Note applyPatch reads content via os.ReadFile(fullPath) (following the link) then rewrites over the link path, so the read and write no longer refer to the same file. atomicfs already used temp+rename before this diff, so it is unaffected; this is specific to the patchapply change.

**Scenario:** Repo has source file util.go that is a symlink to ../shared/util.go (or a hardlink). An LLM-generated unified diff modifies util.go. Before: os.WriteFile updated ../shared/util.go through the link, symlink preserved. After: applyPatch renames a temp over util.go, deleting the symlink and writing a regular file; ../shared/util.go keeps its old content. The edit silently applies to the wrong inode and the link is gone.

**Fix:** Before writing, resolve symlinks (filepath.EvalSymlinks) and write to the resolved real path, or detect os.Lstat symlink/os.Stat nlink>1 and fall back to an in-place O_TRUNC write (os.WriteFile) for those cases so link/inode semantics are preserved; only use temp+rename for plain regular files.

## [MEDIUM/new-bug] RecentActivity applies the cap as a DB LIMIT before scope-filtering, starving the section
`internal/concern/sections/recent_activity.go:16`

Unlike the other scope-filtered sections (PriorDecisions, DissentHistory, SDMAdvisories) which omit any query Limit and cap only at render time, RecentActivity pushes the cap into the ledger query (Limit: maxItems) and then runs filterByScope on the already-truncated result. The ledger query orders by created_at ASC (internal/ledger/index.go:152) and LIMIT takes the first N rows, so the section fetches the maxItems OLDEST mission nodes and then discards the out-of-scope ones. This under-delivers whenever scope dims are set: in-scope recent nodes beyond the oldest maxItems are never fetched, so they can never be rendered. The fix is internally inconsistent with the sibling sections it was written alongside.

**Scenario:** reviewer_for_pr sets recent_activity cap=15 with a scope whose LoopID/BranchID are populated. The mission has 200 nodes, the 15 oldest belonging to a prior loop. The query returns those 15 oldest rows; filterByScope drops all 15 as out-of-scope; the reviewer sees "(no recent activity)" even though the current loop has many recent nodes — they were never fetched because the LIMIT was consumed by older out-of-scope rows.

**Fix:** Drop Limit from the RecentActivity query (fetch all, or use ORDER-DESC in the ledger), run filterByScope, then let renderNodeList(..., maxItems) apply the cap — matching PriorDecisions/DissentHistory/SDMAdvisories.

## [MEDIUM/incomplete-fix] semdiff qualified-key fix still collides for methods on generic types
`internal/semdiff/semdiff.go:102`

symbolKey builds a method identity from s.Recv ("method "+TrimPrefix(Recv,"*")+"."+Name), and Recv is filled by exprString(d.Recv.List[0].Type) at line 359. exprString (line 483) has no case for *ast.IndexExpr / *ast.IndexListExpr, so a generic receiver like *Stack[T] falls through to the default and returns "?" — the whole receiver collapses to "*?". I confirmed this by parsing `func (s *Stack[T]) Len()` and `func (q *Queue[T]) Len()`: both yield Recv="*?" and therefore the identical symbolKey "method ?.Len". The fix disambiguates same-named methods on distinct NON-generic receivers, but for generic receiver types every method with the same name collapses to the same key, exactly the collision the fix set out to eliminate.

**Scenario:** A .go file declares `func (s *Stack[T]) Len() int` and `func (q *Queue[T]) Len() int`. Both map to key "method ?.Len", so oldMap/newMap keep only the last one. If a diff changes only Stack[T].Len's body, Analyze either misses the modification entirely or attributes it to Queue[T].Len — a silently wrong semantic diff on ordinary modern-Go code.

**Fix:** Add *ast.IndexExpr and *ast.IndexListExpr cases to exprString (render the base type name, e.g. render the .X of the index expr) so generic receivers produce a distinct, stable receiver string; then symbolKey disambiguates Stack[T] from Queue[T].
