# Polish-diff review — confirmed findings (2026-07-03)

Independent adversarial review of the 25 polish fixes (branch enhance/sota-wave2-polish, now on main). 6 area-reviewers → every finding double-verified (refuter + path-tracer, unanimous). **7 of 7 raw findings confirmed** — a clean, high-signal review. Notably it caught regressions the polish fixes themselves introduced, including two HIGH sandbox-escape vectors in the git-in-worktree / socket-masking 'containment completion'. The sandbox is opt-in, so blast radius is limited, but a known escape must not ship as 'containment complete'.

Full Go gate (build/vet/test/-race) was green on the polished tree — these are latent behavioral/security bugs, not build breaks.

## [HIGH] WorktreeGitDirs grants write to the entire parent common .git (hooks + config) — sandbox escape via host git execution
`internal/sandbox/policy.go:280`

**Detail:** The new WorktreeGitDirs() returns the linked worktree's per-worktree gitdir AND the parent repo's common dir (e.g. <parent>/.git), and native_runner.go:161 appends both to Policy.AllowWrite (a full read/write bind under bwrap, and a rwAccess Landlock rule / -v :rw docker mount). That makes the common dir's `.git/config` and `.git/hooks/` writable to the sandboxed command. git works fine with a far narrower grant (index/HEAD/logs/refs/objects), but this grants the two files that turn into host code execution: a sandboxed command can write `.git/config` (set core.fsmonitor=/evil, core.pager, core.editor, or core.hooksPath) or drop `.git/hooks/pre-commit|post-commit|post-checkout`. The host runs git against that same repo AFTER the sandboxed command returns — shadow-checkpoint (worktree.ShadowCheckpoint per turn), worktree cleanup (`git worktree remove --force`, `git branch -D`, `git update-ref`, manager.go:207-231), and the final merge/commit — all read the now-attacker-controlled `.git/config` and fire hooks OUTSIDE the sandbox. This defeats the containment the polish wave claims is 'otherwise complete'.

**Failure scenario:** R1_NATIVE_SANDBOX=bwrap on a linked worktree (the native runner's default worktree type). Sandboxed bash writes `<common>/.git/config` adding `[core] fsmonitor = /worktree/evil.sh` (or drops `<common>/.git/hooks/post-checkout`). When the post-turn shadow checkpoint / worktree cleanup / final commit runs git on the host, git executes evil.sh as the host user, outside the sandbox — full escape.

**Fix:** Do not grant the whole common dir. Bind only the specific subpaths git needs writable (objects, refs, packed-refs, logs, index, HEAD, worktrees/<name>) and mount `.git/config` and `.git/hooks` read-only (or omit them). Alternatively run the sandboxed git with GIT_CONFIG_GLOBAL/-c core.hooksPath=/dev/null and treat config/hooks as ro.

## [HIGH] Landlock socket masking does not block connect() to /run/docker.sock — daemon socket still reachable
`internal/sandbox/landlock_linux.go:85`

**Detail:** The fix removes `/run` from landlockROPaths and re-adds only `/run/systemd/resolve`, on the theory that 'anything under /run not listed here is unreadable by construction' and therefore the docker.sock escape is closed on the Landlock backend. That reasoning is unsound: Landlock (through the current ABIs) does NOT mediate connecting to or binding a named AF_UNIX socket — landlock(7) lists this as an explicit limitation. Landlock only gates open/read/write/exec/make/remove/refer/truncate/ioctl on the filesystem and TCP bind/connect (ABI 4). connect() to a pathname unix socket is not a Landlock-handled access, so making /run/docker.sock 'unreadable' does nothing to stop connect(2). Unlike the bwrap backend (which mounts /dev/null over the socket path, genuinely making connect fail with ENOTSOCK), the Landlock backend has no equivalent lever, so the claimed containment is false assurance.

**Failure scenario:** R1_NATIVE_SANDBOX=landlock (or auto with bwrap unavailable) on a host running rootful docker. Sandboxed bash runs `curl --unix-socket /run/docker.sock http://localhost/v1.40/containers/json` or the docker CLI; the connect succeeds despite the socket not being in the read allow-list, giving control of the daemon → `docker run -v /:/host --privileged` → full host escape.

**Fix:** Landlock cannot close this; document it honestly (Landlock backend is not safe against local daemon sockets when the daemon is running) or refuse to select landlock when a reachable daemon socket exists, rather than commenting that removal from the read baseline makes it 'unreadable by construction' (irrelevant to connect()).

## [MEDIUM] Read-only shell commands force a full whole-tree code-graph rebuild (perf regression) _(REGRESSION of: noteShellMutation coarse code-index invalidation after shell commands)_
`internal/tools/tools.go:1073`

**Detail:** handleBash (tools.go:1073) and handleEnvExec (tools.go:1239) now call r.noteShellMutation() unconditionally on EVERY shell command, on all exit paths (the code comment even says success/non-zero/timeout). noteShellMutation (code_tools.go:95) calls r.code.MarkDirty(".") whenever an index has already been built. The next codegraph query — GetDependencies/GetFileSymbols/ImpactAnalysis and every other method — hits refreshLocked() (index.go:155), which unconditionally rebuilds ALL FOUR indexes (symindex.Build + depgraph.Build + tfidf.Build + BuildVectorIndex) over the ENTIRE working tree, regardless of whether the shell command actually mutated any file. There is no read-only detection: `grep`, `ls`, `cat`, `go build`, `go test`, `git status/diff` all re-arm the dirty flag. The registry (and its persistent index) lives for the whole native run — tools.NewRegistry is created once per native_runner invocation (native_runner.go:131) — so this recurs for the entire session. Pre-diff, read-only shell commands never invalidated the index, so graph queries after a build/test cycle were served instantly from cache; that is the behavior this fix regresses. Code-graph tools are registered by default (only R1_DISABLE_CODE_TOOLS=1 removes them), so this is the common path. Correctness is preserved (rebuild always re-reads disk); the cost is latency, mitigable via the R1_DISABLE_SHELL_INDEX_INVALIDATION kill switch.

**Failure scenario:** In a native run on r1-agent (259 Go packages), the agent calls get_file_symbols (builds the index), then runs `go test ./...` via bash (read-only w.r.t. source, but marks the whole tree dirty), then calls get_dependencies -> a full symindex+depgraph+tfidf+vecindex rebuild over the entire repo fires even though no source file changed. Because agents interleave graph queries with very frequent build/test/grep bash calls, essentially every graph tool invocation triggers a multi-second full-tree rebuild for the life of the run.

**Fix:** Do not blanket-invalidate on read-only commands. Either (a) skip noteShellMutation for a curated read-only command set (ls/cat/grep/rg/find/wc/head/tail/pwd/echo, go build|test|vet, git status|diff|log|show), or (b) replace the MarkDirty(".") full-rebuild with an mtime/dir-hash staleness check in refreshLocked so an unchanged tree short-circuits the rebuild. At minimum, gate the invalidation on the command's exit having plausibly written (non-read-only).

## [MEDIUM] docker backend --user host uid:gid breaks the worktree ownership it aims to fix on rootless docker _(REGRESSION of: fix(sandbox): run docker backend as host uid:gid (finding #2))_
`internal/sandbox/docker.go:52`

**Detail:** The fix always passes `--user <host uid>:<host gid>` to make bind-mounted worktree files owned by the invoking user instead of root. That is correct only for ROOTFUL docker. On rootless docker/podman the daemon runs in a user namespace where container uid 0 maps back to the invoking host user and container uid N maps into the host subuid range. Passing `--user 1000:1000` runs the process as container-uid 1000, which maps to a host subuid (e.g. 100999) — so files created in the bind-mounted worktree end up owned by an unreachable subuid, not the host user, and the host user cannot stat/modify/delete them. This reintroduces exactly the failure the comment says it prevents: it breaks the host-side shadow-checkpoint / commit / cleanup. Before this fix (no --user), rootless docker ran as container root == host user and ownership was correct — so this is a regression for rootless users (while fixing rootful).

**Failure scenario:** Host runs rootless docker (Docker Desktop / rootless install / podman). R1_NATIVE_SANDBOX=docker with an image. Sandboxed bash creates or edits files in the worktree; they are owned by host subuid 100999. The subsequent host-side `git` (shadow checkpoint, `git worktree remove --force`, final commit) fails with permission errors on those files; cleanup leaks and the checkpoint/commit breaks.

**Fix:** Detect rootless (docker info -f '{{.SecurityOptions}}' contains 'rootless', or DOCKER_HOST points at /run/user/) and skip --user (or pass --user 0:0) in that case; only pass host uid:gid for rootful daemons.

## [MEDIUM] bwrap daemon-socket mask omits the rootless docker/podman socket under /run/user/<uid>
`internal/sandbox/policy.go:162`

**Detail:** DefaultDenySockets lists only rootful paths (/run/docker.sock, /var/run/docker.sock, /run/containerd, /run/podman, /run/crio, dbus, systemd). Rootless docker and rootless podman expose their control socket under $XDG_RUNTIME_DIR, i.e. /run/user/<uid>/docker.sock and /run/user/<uid>/podman/podman.sock — neither is in the list, so on the bwrap backend they are NOT masked and remain reachable inside the sandbox (bwrap uses --ro-bind / / so the host /run/user tree is present). The fix advertises daemon-socket containment ('a reachable docker.sock is a full host escape regardless of the network posture') but leaves the increasingly-common rootless socket open.

**Failure scenario:** Host runs rootless docker (socket at /run/user/1000/docker.sock, DOCKER_HOST set accordingly). R1_NATIVE_SANDBOX=bwrap. Sandboxed bash runs `docker -H unix:///run/user/$(id -u)/docker.sock run --privileged -v /:/host alpine ...` → mounts host root → escape, because that path was never masked.

**Fix:** Add $XDG_RUNTIME_DIR/docker.sock and $XDG_RUNTIME_DIR/podman/podman.sock (resolve XDG_RUNTIME_DIR, default /run/user/<getuid>) to DefaultDenySockets so bwrap masks the rootless daemon sockets too.

## [MEDIUM] Landlock /run narrowing regresses DNS on non-systemd-resolved hosts _(REGRESSION of: fix(sandbox): mask daemon unix sockets (finding #1) + git in linked worktrees)_
`internal/sandbox/landlock_linux.go:88`

**Detail:** Replacing wholesale `/run` in landlockROPaths with only `/run/systemd/resolve` assumes /etc/resolv.conf always symlinks into systemd-resolved's runtime dir. On hosts using NetworkManager's own resolver (/etc/resolv.conf -> /run/NetworkManager/resolv.conf) or the resolvconf package (/run/resolvconf/resolv.conf), the symlink target now falls outside the allow-list and is unreadable under Landlock, so name resolution fails. Before the fix, /run was granted wholesale and DNS worked on all of these. This silently breaks module/dependency fetches in the execute phase whenever egress is allowed.

**Failure scenario:** Host with NetworkManager-managed DNS (/etc/resolv.conf -> /run/NetworkManager/resolv.conf), R1_NATIVE_SANDBOX=landlock, egress allowed (default). Sandboxed `go mod download` / `npm install` / `git clone https://...` fails to resolve any hostname because the resolv.conf target under /run/NetworkManager is not readable.

**Fix:** Grant the actual resolv.conf target(s) or a slightly broader set: add /run/NetworkManager, /run/resolvconf (and/or resolve the /etc/resolv.conf symlink at policy-build time and grant its target), not just /run/systemd/resolve.

## [LOW] Final-turn shadow checkpoint is lost on the cancel/timeout path because the post-Run flush reuses the dead run ctx _(REGRESSION of: 5be30a78 fix(checkpoint): one shadow checkpoint per turn, recorded after its messages)_
`internal/engine/native_runner.go:694`

**Detail:** The per-tool synchronous take(ctx) was replaced by markDirty (in the tool handler) plus a deferred flush at the top of the NEXT turn's PreTurnHook, with a final post-Run flushCheckpoint(ctx) at native_runner.go:694 to catch the last turn. That final flush passes the SAME ctx that loop.Run used (line 686). When the loop exits via cancellation/timeout, agentloop returns StopReason="cancelled" from its top-of-turn ctx.Done() check (loop.go:507-511) WITHOUT running the next PreTurnHook, so the only remaining flush is the post-Run one — and it runs shadow.flush -> worktree.ShadowCheckpoint under an already-cancelled ctx. ShadowCheckpoint executes several git subprocesses via exec.CommandContext (read-tree/add -A/write-tree/rev-parse/commit-tree/update-ref); under a dead ctx at least one (typically `git add -A`) is killed, so flush returns an error, warnFailure swallows it, and no checkpoint ref or transcript checkpoint marker is created for the last turn's mutation. The old per-tool take() captured that same mutation synchronously while ctx was still live (the tool had just succeeded), so this is a behavioral regression specifically on the common timeout path. Impact is limited: these per-turn checkpoints feed the best-effort resume/timeline feature (checkpoint/resume.go via ListCheckpoints), NOT the workflow's RewindOnRetry (which uses the independently-captured seq-0 rewindBaseline), and the whole mechanism is fail-open. So no data loss or wrong behavior — only a lost rewind-granularity target for the final turn of a cancelled/timed-out dispatch.

**Failure scenario:** A native dispatch's final turn calls write_file successfully (markDirty set). The phase deadline then elapses; at the top of the next iteration agentloop's ctx.Done() check returns "cancelled" and loop.Run returns without another PreTurnHook. The post-Run flushCheckpoint(ctx) at native_runner.go:694 invokes ShadowCheckpoint under the cancelled ctx; git is killed mid-add, flush errors, warnFailure logs once. Result: no shadow checkpoint ref and no transcript checkpoint marker for the last mutation, so a later resume/timeline rewind has no fine-grained target for the final write — whereas the pre-refactor per-tool take() reliably captured it.

**Fix:** Run the post-Run flush (and ideally the deferred flush generally) under a short-lived detached context so a cancelled run ctx doesn't defeat the last checkpoint, mirroring the cortex-shutdown pattern already used in this file (context.Background() with a bounded timeout at native_runner.go:623/628): e.g. `fctx, cancel := context.WithTimeout(context.Background(), 10*time.Second); defer cancel(); flushCheckpoint(fctx)` at line 694.
